# 2026-09-20 深度重构记录

## 目标

将 `SKILL.md` 保持为纯路由入口，把三份官方资料的核心场景转化为可独立运行、可验收的 SOP；移除“快照很短但无法证明 SOP 由何而来”的缺口。

## 发现与根因

| 编号 | 现象 | 根因 | 影响 |
| --- | --- | --- | --- |
| P001 | 原快照只覆盖少量概览，核心场景、分支与护栏不完整。 | 资料层没有按官方章节建立证据锚点。 | SOP 无法回溯到来源。 |
| P002 | SOP 只有命令清单，缺少触发、输入、分支和完成标准。 | 把“会调用 CLI”误当成“可稳定完成任务”。 | 复杂任务容易跳过方法校准、人审、资产复用。 |
| P003 | 根 Skill 混合路由与操作细节。 | 渐进加载边界不清。 | 简单任务也会加载无关命令/风险。 |
| P004 | 运行环境的 CLI 缺失没有被显式作为准入分支。 | 把历史安装/登录与本次可执行状态混淆。 | 容易错误宣称当前 Gateway 或版本已验证。 |
| P005 | `name` 与 description 把产品、CLI 和泛学习词混在一起。 | 顶层发现指针没有以稳定工具入口和专属操作边界组织。 | 可能误触发泛学习、泛 Partner 或非 YAI 的 AI 任务。 |
| P006 | 名称与 GitHub 仓库身份不一致。 | 机器名已改为 YAI CLI 工作流，但用户选择以“一堂 YAI Skill”作为统一品牌。 | 调用名、展示名和仓库地址不易对应。 |
| P007 | 人读 README、根入口与 SOP 时，术语密集且同一规则重复出现。 | 内容按“证据与控制”组织，而不是按“用户要做的事”组织。 | 新用户难以找到入口，维护时也容易读到重复规则。 |
| P008 | SOP 与资料、入口分列在顶层，目录职责不直观。 | SOP 被当作独立运行层，而实际是按任务加载的参考资料。 | 阅读目录时难以理解从入口到执行说明的关系。 |
| P009 | description 把 Skill 缩成 CLI 操作，课程方法挖掘停留在“查询”。 | 没有把 CLI 当成连接入口，也没有把课程材料、方法提炼和真实验证拆成连续步骤。 | Skill 容易退化为命令说明，不能帮助用户把课程用进工作。 |

## 改动

- 三份快照改为带来源、采集边界、证据锚点和 SOP 落点的结构化语义快照；明确不是全文导出。
- 新增“证据到执行”地图，覆盖 R0 准入、R1 方法学习、R2 Partner、R3 接力、R4 执行、R5 会话、R6 资产/封装。
- 重写五份独立 SOP：准入、学习、Partner、执行、会话；每条包含适用范围、步骤/分支和完成标准。
- 根 Skill 限缩为路由与共享护栏；未将官方 CLI 说明复制进根文件。
- P005：description 以 `whyai` CLI 作为稳定入口，仅覆盖一堂 YAI 专属的准入、数据读取、Partner/会话、保存/导出四类动作，并排除泛学习和非 YAI Partner 任务。
- P006：统一目标身份为 `yitang-yai-skill`；同步前置 `name`、展示名称、默认调用名与 README 标题。GitHub 仓库改名待已登录网页会话执行后，再更新本地 remote。
- P007：README 改为人读导航；根入口只保留路由和四条共同规则；SOP 统一改为“什么时候用 → 怎么做 → 做完后确认”；资料页改为简明来源说明。保留原有授权、最小读取、来源校验和人工确认边界。
- P008：将 `sops/` 迁移到 `references/sops/`，入口链接同步更新；源码目录从 `yitang-skills` 迁移到 `yitang-yai-skill`。根 `SKILL.md` 保持 Codex 所需固定文件名。
- P009：description 改为“课程方法 → Partner 协作 → 真实任务 → 资产”的工作流定位，明确 CLI 是连接入口。新增不含个人数据的课程运行时观察；学习 SOP 将扩展为“课程内容挖掘、方法卡、真实验证、课程对象查询”。
